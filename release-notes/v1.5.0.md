Local helper that prints POS receipts and labels on a venue's own hardware — over the network
(ESC/POS-over-TCP), a USB print queue, or a serial/Bluetooth port. It runs on a venue PC, not
inside the POS terminal's PWA, because a browser cannot open any of those. It also dials out to
the cloud API, so a phone or tablet can print through it without reaching the LAN. Install it on
**every till**, not on one shared PC.

**1.5.0 is a drop-in upgrade.** Nothing on the LAN surface changed: `POST /print` with
`{ip, port, payload_base64}` still answers `{ok:true}`, the registry and job queue behave exactly
as in 1.4.0, and `relay.json` is kept — an upgraded bridge does not re-enroll or show up as a
second entry in the POS.

## What's new in 1.5.0

**Your USB and Bluetooth printers are now reachable from an iPad or an Android tablet.**

A tablet cannot run this bridge, cannot open a TCP socket from a browser, and — because the POS
is served over https — cannot even call a bridge on the LAN. Its only path has always been the
cloud relay, and a relayed job could only carry an `ip:port`. That is fine for a network printer
and useless for a USB one, which has no address for a remote till to send. The workaround was to
invent a private-looking IP, alias the USB entry to it, and type the same fake address into the
POS.

Two additions remove that:

- **The bridge now reports its own printers upstream.** Every heartbeat, and the enrolment POST,
  carries `registry_printers` — a summary of `printers.json` (id, name, transport, type, enabled,
  address, port), capped at 64 entries. That is what lets a device with no LAN access list the
  printers on a network it cannot see.
- **A cloud job may name a printer by id.** `printer_id` resolves through `findPrinter` and takes
  precedence over `target_ip`, which may now be absent. The address path is untouched, and
  `resolveByAddress` still honours an existing fake-IP alias, so nothing configured that way
  breaks.

Both are additive in both directions: an older API strips the new field, and a server that sends
no `printer_id` gets exactly the 1.4.0 behaviour. A bridge older than 1.5.0 simply never appears
as an option for its USB printers.

Pairing itself is also finally reachable: **POS Settings → Printing → Connection** now issues the
enrolment code this binary has always asked for. Until now the README told operators to get a code
from a screen that did not exist.
