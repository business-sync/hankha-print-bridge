# 1.14.5 — a proxy that blocks websockets no longer stops cloud printing

**Drop-in upgrade** (`relay.json` / `printers.json` untouched). Only the cloud relay changed:
printers, the queue, keep-warm and `POST /print` behave exactly as in 1.14.4.

## What was wrong

- **A refused websocket looked like a revoked token.** An edge, proxy or WAF that blocks
  websocket upgrades but passes ordinary HTTP answers the handshake with a 401, the same status
  the API gives a dead token. The bridge believed it. It sat in the rejection backoff re-reading
  its saved token and never fell back to the long-poll, which would have worked the whole time.
  One proxy setting could stop a venue's cloud printing until someone re-paired a bridge that was
  never unpaired.
- **A lost result report left a printed ticket "unconfirmed".** The bridge reported each job's
  result once. A network blip or a 5xx was the end of it: the server's sweeper then marked the
  job UNKNOWN, the POS showed the ticket as unconfirmed, and the operator was invited to reprint a
  receipt that may already have come out.

## What changed

- **A handshake 401 is checked before it is believed.** The bridge sends one ordinary heartbeat
  with the same token. Only a 401 there means the token is revoked, handled as before (pair
  again). Any other answer means something in front of the API refused the upgrade: the bridge
  logs `relay.ws.refused` once, keeps printing over the long-poll, and tries the websocket again
  after `PRINT_BRIDGE_WS_RETRY_MS` (default `1800000`, 30 minutes, the same window a server
  without a websocket route already got). This applies in `auto` and `ws` mode alike.
- **A heartbeat that fails is not a refusal.** If that heartbeat gets no answer, or answers 5xx,
  408 or 429, the API is having a bad minute, which says nothing about the network in front of it.
  The bridge takes the ordinary transient path (one long-poll, then the websocket again) instead
  of blocking the websocket for 30 minutes.
- A close frame 1008/4401 on a websocket session that had opened is still a revocation, and is
  not checked.
- **Result reports are retried.** A result that fails to send with a network error, a 5xx, a 408
  or a 429 is sent again up to three more times, about 1 s, 2 s and 4 s apart (jittered). A 2xx or
  409 is final; any other 4xx is given up at once, as before. Reports no longer hold up the poll
  loop: the three early-refusal reports now go in the background like every other report. When
  the bridge is stopped, a report still waiting to retry is given up with a log line instead of
  silently.
- **New and changed log events:**
  - `relay.ws.auth_probe` (debug): the heartbeat that checks a handshake 401.
  - `relay.ws.refused` (warn, once per process): the upgrade was refused but the token is good.
  - `relay.ws.blocked` now says `because=unsupported` or `because=refused`.
  - `relay.result.retry` (warn, gated) and `relay.result.reported` (info): a report that needed
    another try, and the one that got through.
  - `relay.result.failed` now carries `attempts`, and `shutting_down` when a stop cut it short.
- **README:** `PRINT_BRIDGE_WS_RETRY_MS` is in the environment table. The
  `PRINT_BRIDGE_SYNC_TIMEOUT_MS` row now says the POS waits 12 s, 4 s longer than the bridge, so it
  hears whether a ticket may already be on paper before it fails over. Keep the bridge's value
  under the POS's.

## What to look for after installing

- `starting hankha-print-bridge v1.14.5`, and `"version":"1.14.5"` from `GET /health`.
- `relay.ws.refused` means the token is fine and a proxy, WAF or edge on the way to the API does
  not pass websocket upgrades. Printing continues over the long-poll. The fix is on that network,
  not a re-pair.
- `relay.result.retry` followed by `relay.result.reported` is a report that survived a blip.
  `relay.result.failed … attempts=4` is one that could not be delivered at all; the POS will show
  that ticket as unconfirmed, as it did before.
