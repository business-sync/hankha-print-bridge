# 1.14.7 — the relay works again on Windows tills, and a refused certificate is diagnosed, not presumed

**Drop-in upgrade** (`relay.json` / `printers.json` untouched). The cloud relay's TLS handling, its
diagnostics and the status page changed; printers, the queue, keep-warm, `POST /print` and both
relay transports otherwise behave exactly as in 1.14.6. **Install this on every Windows till
running 1.14.4, 1.14.5 or 1.14.6.**

## What was wrong

- **Every `fetch` to the cloud failed on Windows from 1.14.4 on, while the websocket connected.**
  Heartbeats, the pairing announce, job result reports and scan results all failed with
  `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` from the first second after the upgrade, in the same second
  as `relay.ws.open`. The certificate was the real one (`CN=hankha.la`, issued by Google Trust
  Services WE1, chaining to GTS Root R4 — one of the 144 roots compiled into the binary), and
  Windows itself validated it. The cause is a Bun bug, not the till: Bun 1.3.11's one-time
  root-certificate setup is not thread-safe ([oven-sh/bun #28612](https://github.com/oven-sh/bun/issues/28612),
  fixed in 1.3.13). The first TLS context on each thread triggers the setup, the "done" flag is
  raised before the list is full, and a second thread arriving in that window builds its trust
  store from a partial list and keeps it. `fetch` runs on Bun's HTTP thread; `new WebSocket()` on
  the JavaScript thread. 1.14.4 moved the websocket onto Bun's native client — before that the
  handshake went over `node:https`, which shares `fetch`'s context — so from 1.14.4 the first
  heartbeat and the first socket dial raced at start-up, and on a Windows till the HTTP thread
  lost. macOS and Linux never showed it: Bun also loads `/etc/ssl/cert.pem` into every store
  there, separately from the racing list, and it carries GTS Root R4 too.
- **1.14.6 called that an antivirus.** It assumed every trust-code failure was HTTPS inspection,
  told the shop to exclude the bridge from scanning or add a root certificate, and the watchdog
  restarted a bridge whose websocket was fine every fifteen minutes. Neither remedy could have
  helped, and both widen trust.
- **A heartbeat refused on trust grounds was never classified.** Only the websocket handshake and
  the poll reached the classifier, and a websocket that opened cleared `last_error` — so a bridge
  in exactly the state above showed "connected" with nothing to say about the heartbeats and
  result reports it was losing.

## What changed

- **The race is closed three ways**, each sufficient on its own:
  1. `src/tls-warmup.ts` finishes the runtime's root-certificate setup on the main thread
     (`tls.getCACertificates()`) first thing in `index.ts`, before any connection, so every later
     thread finds the list complete. Logged at debug as `tls.warmup`.
  2. The binary is compiled on **Bun 1.3.14** (the fix landed in 1.3.13; 1.3.14 is the newest
     1.3.x and keeps `tls.ca` additive). `scripts/package.mjs` refuses to compile on anything
     older than 1.3.13. The startup line says which runtime a till runs:
     `app.starting … runtime="bun 1.3.14"`.
  3. `src/relay-fetch.ts`: a relay request that fails on trust grounds is retried once with the
     runtime's own roots — the bundled list plus `NODE_EXTRA_CA_CERTS`, the exact set `fetch` was
     meant to use — passed explicitly. If that verifies, it is logged once as
     `relay.tls.explicit_roots` with the runtime version, every later relay request carries the
     roots, and the Cloud relay card shows *Trust workaround: bundled roots passed explicitly
     since …*. Nothing on the computer changes and no root is trusted that was not already.
- **A refused certificate gets a verdict, not a presumption** (`src/tls-trust.ts`). The bridge
  reads the certificate back, asks `node:tls` in its own process whether it accepts the chain,
  checks whether the issuer is a public authority, folds in the explicit-roots retry, and logs
  `relay.tls.untrusted` with `kind=`:
  - `runtime` — the certificate is real and this build refused it: "update the Print Bridge; do
    not change antivirus settings or add root certificates for this". The page says *This bridge
    version cannot verify Hankha's certificate* with the runtime version.
  - `intercepted` — self-signed, or issued by something no browser trusts, and nothing here
    accepts it: a program on this computer re-signs HTTPS. The page names the issuer and asks
    whoever manages the computer to stop that program inspecting the bridge's connection. No
    page or log line tells a shop to exclude the bridge from scanning or to add a root; the
    README keeps `NODE_EXTRA_CA_CERTS` as an administrator's route for this kind only.
  - `unverified` — the certificate could not be read back: update, then send `bridge.log`.
  The line also carries `origin` (websocket, poll, **heartbeat, result, scan** — the last three
  are new), `runtime`, `authorized` and `authorization_error`. `/health` and `/pairing` carry the
  verdict as `relay.tls_trust` and the workaround as `relay.explicit_roots_since`; the verdict
  outlives a websocket that opens and clears on the next relay request over HTTP that verifies.
- **The status page follows the verdict.** Three leads and three pairing-screen states instead
  of one, a *Certificate* row and a *Trust workaround* row on the Cloud relay card, in all seven
  languages. The code field and the Re-pair button are unchanged.
- **README** "Cloud jobs → The bridge cannot verify api.hankha.la (TLS trust)" replaces "HTTPS
  inspection / corporate proxy": the three verdicts, the race and its three fixes, the
  interceptor-root procedure moved under an administrators-only heading, and why
  `--use-system-ca` is still not compiled in. The Windows README and the logging catalogue
  (`relay.tls.untrusted`, `relay.tls.explicit_roots`, `tls.warmup`) match.
- **`scripts/tls-probe/`**: a stand-alone probe (`probe.ts`, cross-compiled with
  `bun build --compile --target=bun-windows-x64`) that runs `fetch`, `node:https`, `node:tls` and
  `WebSocket` against `api.hankha.la` and four public hosts, tries `fetch` with each root passed
  explicitly, and has a `race` mode that reproduces the start-up order. Run it as SYSTEM (the
  account the scheduled task uses) on a till that still shows a `runtime` verdict.
- Bun's WebSocket client **does** verify certificates (since Bun 1.0.8): the probe's
  `untrusted-root.badssl.com` and `self-signed.badssl.com` checks fail its handshake. A `wss://`
  that connects is a verified connection.

## What to look for after installing

- `starting hankha-print-bridge v1.14.7 … runtime="bun 1.3.14"`, and `"version":"1.14.7"` from
  `GET /health`.
- On a till that showed the fault: `relay.heartbeat` accepted, `relay.ws.open`, no
  `relay.tls.untrusted`, no `relay.tls.explicit_roots`, and the POS Printing page showing the
  bridge online. `relay.tls.explicit_roots` appearing means the workaround carried it — it works,
  and the log line is worth sending in.
- `relay.tls.untrusted kind=runtime` on 1.14.7 should not happen; send `bridge.log` and the
  probe's output. `kind=intercepted` names a program on that computer in `issuer=`.
