Local helper that prints POS receipts and labels on a venue's own hardware — over the network
(ESC/POS-over-TCP), a USB print queue, or a serial/Bluetooth port. It runs on a venue PC, not
inside the POS terminal's PWA, because a browser cannot open any of those. It also dials out to
the cloud API, so a phone or tablet can print through it without reaching the LAN. Install it on
**every till**, not on one shared PC.

**1.8.0 is a drop-in upgrade.** `relay.json` and `printers.json` are both kept as they are — an
upgraded bridge does not re-enroll, does not appear twice in the POS, and needs nothing added to
its registry to carry on doing what it did in 1.6.0. Everything new below is either an addition
or a fix to something that was already wrong.

> This release also carries **1.7.0**, which was numbered but never published.

## Receipts

**Kip totals no longer wrap onto their own line.** Two-column lines were padded by counting
characters, but the encoder expands as it writes: `₭` becomes `LAK`, `…` becomes `...`, `½`
becomes `1/2`. `₭25,000` is seven characters and nine printed columns, so every total overran its
line by two and pushed the price down a row — on essentially every receipt in a kip-denominated
venue. Widths are now measured in what actually reaches the paper, and a name too long for the
line is cut on a character boundary rather than mid-symbol.

**An over-long barcode is rejected instead of printed as commands.** `GS k` announces its payload
in a single byte, and a value longer than that used to wrap silently: the printer read the
announced number of bytes as barcode data and then read the rest of the receipt as instructions —
random cuts, a drawer kick, a metre of garbage. Anything over 255 bytes is now a plain
`payload-rejected` with the reason, and nothing is sent.

**A bad `dots_per_line` or `codepage` is reported rather than swallowed.** Both were validated
after the parser had already decided the document was fine, so an out-of-range value answered
`200` and quietly printed at the fallback width. It is now a `400` naming the field.

## Printing from a phone or tablet

A tablet is paired to a station it cannot see. It does not know one printer id from another, and
it has no idea whether the roll in the kitchen is 58 mm or 80 mm. Two additions close that gap:

- **Printers can be tagged with a role** — `receipt`, `kitchen` or `bar` — in `printers.json`,
  alongside the existing `type`. `type` is what the hardware *is*; role is what it is *for*, which
  only the operator knows. Two printers can both be receipt rolls and still be the bill printer
  and the kitchen pass. The tag is optional, and untagged is a meaningful state: the server treats
  an untagged receipt printer as the venue's bill printer so role addressing works before anyone
  has configured anything, and refuses to guess for `kitchen`/`bar`, where guessing wrong prints a
  bar ticket on a customer's bill. The role each bridge holds is reported upstream on every
  heartbeat, so the POS can address a slip by role instead of by id.
- **The bridge can render a slip itself.** A relay job may now carry a structured `document`
  instead of pre-rendered bytes, and it is rendered here, at the real paper width of the printer
  that will print it. Same parser, same size cap, same errors as `POST /jobs` — only the printer
  resolution differs. A document that cannot be rendered reports `printed_certainty: 'none'`, so
  the POS knows it may safely offer to print again rather than sending someone to check a cable.

## Printing from the till

**`POST /print` now accepts `printer_id`.** This is the only way the synchronous route can reach a
USB or serial printer — one wired to this machine has no address to dial, so the `ip`/`port` form
could not express it at all, and the POS could see such a printer in the registry and not print to
it. The address form is untouched.

**`POST /print` now accepts `job_id`, and a repeat of one replays instead of reprinting.** The
cloud path has been idempotent since it existed; the local path — which is what every desktop till
actually uses — had nothing, so a double-tapped button or a `fetch` the browser retried was simply
a second bill in the customer's hand. The answer to a replay is the *first* outcome, so a retry of
a job that failed still reads as a failure. A job that provably never reached the printer stays
retryable, so switching a printer back on and pressing Retry works.

## Status page

The page at `http://localhost:9200` gains the two things an operator previously needed a terminal
for — on a machine where the binary is not on PATH after the macOS installer:

- **A "find printers" card.** It sweeps the LAN and lists what answered, marks devices already in
  the registry, and offers a ready-made `printers.json` entry to copy. It still writes nothing.
- **Job history with a Cancel action**, and a per-row **Identify** button that asks a printer which
  language it speaks — the root cause of the whole "it prints garbage" class of fault, and
  otherwise invisible, because the printer is online and the job succeeds. Identify is offered only
  where it can work, and it warns before you press it that it may print a few stray characters.

Also on the page: every request is bounded by a timeout, so a printer that accepts a connection and
then goes quiet can no longer freeze the whole page; test results appear on a fixed line instead of
growing the row and shunting the printer you are watching down the screen; "could not load" and
"nothing has printed" are now different sentences; the http-only warning is no longer printed
underneath an `https://` address; and state changes are announced to screen readers. Lao printer
names now render on stock Windows tills, which have neither Noto Sans Lao nor a Lao-capable
`sans-serif` and were falling through to boxes.

## Reliability

- **The service survives an unexpected throw.** An unhandled rejection ends a Node process by
  default, and this one is a printer daemon with no window — it comes back only when launchd or
  Task Scheduler notices, and the evidence is a till that stopped printing. Off-request failures
  are now logged loudly and the bridge keeps taking jobs; an unexpected throw inside a route
  answers `500` instead of leaving the caller's socket open until its own timeout.
- **A dropped relay connection no longer reconnect-storms the API.** Only a deliberate close counts
  as a clean one now. An abnormal close — a TCP reset, a load balancer dropping the upgrade — was
  treated as a served session, which reset the failure count and reconnected with no delay at all;
  a balancer that accepted and immediately dropped produced an unbounded loop with a registry read
  per turn. Every reconnect also has a floor under it.
- **Test print answers within 12 seconds.** It used to hold the HTTP request open for a full minute
  against a printer that was switched off, which stopped the status page updating until it was
  reloaded.
- **`/status` reports where `printers.json` actually is** — on `/status` rather than `/health`,
  because `/health` is unauthenticated and that path contains the account name on macOS.
- `/health` answers `HEAD` as well as `GET`, for uptime monitors. Cancelling an unknown job id is a
  `404` instead of "already printing or finished" — the one answer that tells a caller not to
  retry. `/status` no longer loses every row because one printer's driver could not be asked, and
  no longer counts a container or Kubernetes pod address as an ordinary LAN interface.
- A non-boolean `enabled` in `printers.json` is now an error. A stringified `"true"` from a script
  read as `false`, so the `PUT` answered `200`, the printer was silently disabled, and every job
  afterwards failed with "printer is disabled" while the config on screen said the opposite.

## Security

**A job id can no longer escape the spool directory.** Ids arrive from `POST /jobs` and from the
relay, become a filename, and were unchecked: `../../../../tmp/x` wrote a caller-influenced file
outside the state directory and deleted that path when the job settled. Even an innocent `a/b`
broke spooling. Ids are now constrained, and a bad one is a `400` naming the field rather than a
substituted id — silently minting a fresh one would turn a retry into a second receipt.

## macOS installer

**The .pkg no longer installs a daemon that can never start.** Opening `Hankha Print Bridge.app`
from the .dmg registers a per-user LaunchAgent under the same label, on the same port, and booting
out the system daemon alone left it holding 9200 — so the daemon the package installed failed to
bind on every launch, forever, while the .dmg copy answered for it and the POS reported a version
that did not match what was just installed. The package now removes that agent for every account on
the machine, and confirms the process answering on 9200 is the one launchd started for this label
rather than trusting that *something* replied.

## Pairing

A failed enrolment now says why. The API's response body was thrown away and every failure read as
`Enrollment failed: HTTP 500`, so a named, recoverable condition — this computer already holds a
bridge row in the venue — was indistinguishable from the API being down, on both the pairing page
and the CLI. The server's own message is shown, with the request id when there is one.
`--enroll` also normalises a pasted code the same way the pairing page does, so a lowercase or
mistyped code is answered instantly instead of spending one of the five enrolment attempts a minute.
