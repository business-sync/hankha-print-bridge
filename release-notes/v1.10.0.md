# 1.10.0 — the "This computer" card

Restarting the bridge, stopping it starting at boot, removing it, restarting the till and
clearing a jammed queue all needed a terminal until now: `launchctl kickstart`, an elevated
PowerShell, `sudo /usr/local/hankha/print-bridge/uninstall.sh`. The person standing at the till
is a café owner. This release puts all five on the page the installers already tell them to open.

## What is new

Open <http://localhost:9200> and scroll to **This computer**. It names what is running the bridge
and where its files are, and offers five things — each of which says what it cannot do, and hands
over the command that does it by hand when it cannot.

**Restart the print bridge.** Stops cleanly and lets launchd or Task Scheduler bring it back. The
page then waits for a process id that is *not* the one it stopped, because something answering on
port 9200 is not the same as the bridge coming back. It is **refused outright on a bridge nothing
would restart** — that button on an unsupervised install leaves a till with no bridge at all.

**Start automatically.** Only appears when the bridge is not already registered. On macOS it
writes the LaunchAgent and hands the port over, with no administrator password. On Windows it
runs `install.ps1 -SkipCopy`, the same call the Setup.exe makes.

**Remove from this computer.** Three scopes, named for what survives: stop it starting, remove
its files too, or remove everything including printers and pairing. **The log file always
survives** — it is the only record of why a till stopped printing. The confirmation asks for the
machine's name to be typed.

**Restart this computer.** Sixty seconds with a Cancel, and it refuses while jobs are still
queued unless told a second time. Queued jobs survive in the spool and print on the way back up.

**Clear stored print data.** A checklist, not a button: waiting jobs, recent job records,
duplicate protection and the log files, each with its count and size. Clearing duplicate
protection is **off by default and says why** — it is what stops a job the server redelivers from
printing a second bill. `printers.json` and `relay.json` are never touched by any of it.

## Why the controls are locked to the machine itself

Every other route on the bridge is CORS-open to the venue LAN, which is the right trade for
printing and the wrong one for rebooting a till: with those headers, any web page an operator
opened on the till could reboot it, and a DNS-rebinding page could do it from outside the venue.

`/service/*` therefore has its own gate: loopback only, **no CORS headers at all** — so a
cross-origin request fails its preflight and never arrives — an `Origin`/`Sec-Fetch-Site` check
for the form POST that skips a preflight, a `Host` pin against rebinding, and a single-use
confirmation token minted by `GET /service`. One action at a time, and every attempt is logged.
Opened from another terminal on the LAN, `GET /service` answers 403 and the card is simply not
there.

`PRINT_BRIDGE_TOKEN` still applies on top of all of it. Set `PRINT_BRIDGE_SERVICE_CONTROL=off` to
remove the family entirely on a managed fleet.

## Also in this release

- The card is in all five languages, like the pairing screen. Paths, versions and machine names
  stay as they are.
- The installers now stamp `PRINT_BRIDGE_MANAGED`, so the bridge knows what is supervising it
  without asking launchd or `schtasks`. Bridges installed before this work it out by probing.
- Fixed: clearing the spool removed the spool file of the job that was **being printed at that
  moment** — the only record that it had been sent, and what a crash mid-print is recovered from.

## Endpoints

```
GET  /service                what supervises this bridge, where its files are, what may be done
GET  /service/cache          what a clear would remove, itemised with sizes
POST /service/restart        POST /service/autostart      POST /service/uninstall
POST /service/reboot         POST /service/reboot/cancel  POST /service/cache
```
