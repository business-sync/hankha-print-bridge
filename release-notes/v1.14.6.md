# 1.14.6 — an antivirus or proxy that inspects HTTPS is named, not mistaken for a dropped uplink

**Drop-in upgrade** (`relay.json` / `printers.json` untouched). Only the cloud relay's diagnostics
and the status page changed: printers, the queue, keep-warm, `POST /print` and both relay
transports behave exactly as in 1.14.5.

## What was wrong

- **HTTPS inspection looked like a network blip.** The bridge verifies `api.hankha.la` against
  the root certificates compiled into its binary, not the ones the operating system trusts. On a
  PC where an antivirus (Kaspersky, ESET, Bitdefender, Avast…) or a corporate proxy re-signs every
  TLS connection, the bridge is handed a certificate it has never heard of and every relay attempt
  fails, for good, with `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`. The bridge read that as an uplink
  drop that "usually reconnects on its own", and the disconnected screen offered a new pairing
  code. Neither waiting nor re-pairing fixes it. LAN printing kept working; cloud jobs stopped.

## What changed

- **A TLS-trust failure is told apart from a dropped uplink** (`src/tls-trust.ts`). The five
  OpenSSL trust codes — `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, `SELF_SIGNED_CERT_IN_CHAIN`,
  `CERT_UNTRUSTED`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `DEPTH_ZERO_SELF_SIGNED_CERT` — are
  recognised in whichever shape the runtime throws them, on the long-poll and on the websocket
  handshake alike.
- **The log names the interceptor.** On such a failure a gated `relay.tls.untrusted` line (warn,
  once per ten minutes, right after the usual `relay.retry` line) carries the issuer, subject,
  SHA-256 fingerprint and validity of the certificate that was presented, beside the remedy. It
  comes from one extra connection opened *without* verification purely to read who signed the
  certificate; nothing is sent over it, and every real request keeps verifying exactly as before.
- **The status page says what to do.** The Cloud relay card's lead becomes "Something on this
  computer is inspecting HTTPS" with the two remedies as its steps, and the pairing screen shows
  the same instead of "This computer was disconnected / Get a new code". The code field and the
  Re-pair button are unchanged. All seven languages.
- **The remedies are documented** in README "Cloud jobs → HTTPS inspection / corporate proxy" and
  in the Windows README, in the order to try them:
  1. Exclude the bridge from HTTPS scanning in that program, by process (`hankha-print-bridge.exe`;
     on macOS the `hankha-print-bridge` binary) or by host (`api.hankha.la`), then restart the
     bridge.
  2. Export that program's root certificate to a PEM file and point `NODE_EXTRA_CA_CERTS` at it:
     a line in `bridge.env` on Windows (`Add-Content -Encoding ascii`; setup.exe and install.ps1
     rewrite that file on every upgrade, so add it again afterwards), the LaunchDaemon plist on
     macOS. The binary honours it for `fetch`, `node:https` and its WebSocket alike, in addition
     to the bundled roots.
- Bun's `--use-system-ca` was evaluated for the Windows and macOS builds and **not** compiled in:
  that a root in the OS store is then trusted could not be shown from the build machine. The
  README records the evidence and the two runs that would settle it; `scripts/package.mjs` says
  why the flag is absent. `NODE_EXTRA_CA_CERTS` is the supported route.

## What to look for after installing

- `starting hankha-print-bridge v1.14.6`, and `"version":"1.14.6"` from `GET /health`.
- `relay.tls.untrusted … issuer="…"` after a `relay.retry` line names the program inspecting
  HTTPS. Fix it in that program, or with `NODE_EXTRA_CA_CERTS`; a re-pair will not help.
- On <http://localhost:9200>, a Cloud relay card reading "Something on this computer is inspecting
  HTTPS" is the same fault, with the steps to take.
