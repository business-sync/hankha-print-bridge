# 1.12.0 — pairing on one computer

Until now pairing always needed two devices. This machine put a QR code on screen and somebody
scanned it with a tablet. That is the right flow for a venue where the till is a tablet and this
is the PC by the printers — and it is nonsense in the shop where they are the same computer,
which is most of them. There is no camera to point at the screen it is on, so the operator was
reading eight characters out of one window and typing them into another on the same monitor.

**Open <http://localhost:9200> and the page now leads with "Pair on this computer."** Press it
and the browser lands in Hankha with the code already filled in. The QR is still there,
underneath, for the venues that need it.

The installers already open this page when they finish, so on a new computer that is the whole
setup: install, press one button, confirm in Hankha, print a test slip.

## The same link, from the other side

The till's Connect wizard gained a **This computer** path that opens the same link itself — for a
bridge that was installed weeks ago, where nobody is standing in front of this page.

Both are one route, `GET /pairing/handoff`, which redirects into the till with the live code
appended. It exists because the obvious design does not work: a page served over HTTPS can never
`fetch` `http://localhost:9200` — mixed content and Private Network Access both forbid it — and
that is why the tablet has always talked to the cloud rather than to this process. A **top-level
navigation** is not subject to either rule, so one redirect crosses the wall in both directions
and behaves identically on production and on a developer's laptop.

The code is appended at the moment of the request, never stored with the URL attached. A pairing
session renews its code silently every fifteen minutes, and a link built when the session was
announced would keep offering the one before it.

## Where the till address comes from

The server tells this bridge, in the same answer that carries the pairing code — a new
`POS_BASE_URL` on the API. Nothing is configured here, and a bridge cannot guess it: the address
of the till is not derivable from the address of the API.

**Blank is a supported answer and means "do not offer it".** The button is hidden rather than
shown broken, and `/pairing/handoff` redirects to this page instead of erroring, where the code
is on screen to be typed the old way. That is also what happens in the seconds before the first
code arrives.

## Security

`/pairing/handoff` is **loopback-only**, like `/pairing` and `/enroll`, and checked in the same
place so no later edit can widen it by accident. It is the sharpest case of the three: the code
travels in a `Location` header that a browser follows, so anyone who could reach it from the
venue wifi could claim this computer into their own organisation.

It grants nothing new. `/pairing` already hands the same code to anything that can reach
loopback; this only saves the operator from retyping it.

## Also in this release

- The redirect is sent `Cache-Control: no-store`. A cached one would keep pointing at a code that
  has since been renewed or spent, and the till would call it invalid.
- The new strings are in all five languages, like the rest of the page.
- **1.12.0 is a drop-in upgrade.** `relay.json` and `printers.json` are untouched, no bridge
  re-enrolls, and nothing about printing changed.

## Endpoints

```
GET  /pairing/handoff        302 into the till with the live pairing code
```
