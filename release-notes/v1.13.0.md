# 1.13.0 — the bridge knows how wide its paper is

**1.13.0 is a drop-in upgrade.** `relay.json` and `printers.json` are kept as they are; an
upgraded bridge does not re-enroll and does not appear twice in the POS. It changes one thing: a
receipt that was laid out for wider paper than the roll it is about to print on is now refused
instead of wrapped.

## What was wrong

A print job can arrive as a **document** — a described slip the bridge lays out itself — rather
than as finished bytes. That exists because the device sending it often cannot see the printer: a
phone or a tablet is paired to a station in another room and has no idea whether the roll is
58 mm or 80 mm.

A document may also pin a width, `dots_per_line`, meaning "this is already laid out — do not
re-flow it". The bridge took that pin at face value. Send a slip pinned to 80 mm to a 58 mm
printer and every row was too long for the head, so the printer wrapped each one onto a second
line: columns staggered, totals landed in the middle of a line, and the job still reported
success. Nothing anywhere said the paper was the wrong size, so it read as a broken printer.

The API could not catch it either, because nothing ever told it how wide each printer was.

## What changes

- **Every heartbeat now reports each printer's `dots_per_line`**, alongside the name, transport
  and role it already sent. Null for a label printer, which has no line width. This is what lets
  the API refuse an over-wide slip before it is queued, so the till can rebuild it for the
  narrower roll and print it correctly on the first attempt.
- **A slip pinned wider than the paper is refused**, naming both widths and what to do about it —
  `422 render-failed` on `POST /jobs`, `payload-rejected` over the relay. A slip pinned *narrower*
  still prints, unchanged: 58 mm artwork on an 80 mm roll is merely narrow, and venues running
  mixed rolls rely on that.
- A document that pins **no** width behaves exactly as before, and is still the right way to send
  one: the bridge lays it out for whichever printer it ends up on.

Nothing else changed. Raw `payload_base64` jobs are untouched — the bridge cannot inspect bytes
and has never pretended to.
