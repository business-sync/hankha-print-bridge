Local helper that prints POS receipts and labels on a venue's own hardware — over the network
(ESC/POS-over-TCP), a USB print queue, or a serial/Bluetooth port. It runs on a venue PC, not
inside the POS terminal's PWA, because a browser cannot open any of those. It also dials out to
the cloud API, so a phone or tablet can print through it without reaching the LAN. Install it on
**every till**, not on one shared PC.

**1.6.0 is a drop-in upgrade.** Nothing existing changed: the LAN surface, the registry, the job
queue and the relay all behave exactly as in 1.5.0, and `relay.json` is kept — an upgraded bridge
does not re-enroll or appear twice in the POS.

## What's new in 1.6.0

**You can pair this bridge from its own page. No terminal.**

Pairing used to mean running `hankha-print-bridge --enroll <code>` — the command the POS printed
on screen, and a command that could not be run as shown on either platform we ship:

- On **Windows** the binary is at `%ProgramFiles%\Hankha\Print Bridge\hankha-print-bridge.exe`.
  The installer registers a scheduled task and a Start-Menu shortcut, but nothing on PATH, so
  typing the command gave `command not found`.
- On **macOS** the .dmg keeps the binary inside the app bundle — same result.
- On the macOS **.pkg** it was worse than a plain failure. The daemon runs as root, so a bare
  `--enroll` wrote the token to the operator's own `~/Library/Application Support/…`, printed
  `Enrolled as bridge …`, and then never connected, because the daemon reads a different file.

Open `http://localhost:9200` on the machine and there is now a **pairing box** on the Cloud relay
card. Paste the code from Settings › Printing, press Connect, done — the relay starts immediately,
without restarting the service.

- `POST /enroll` `{code}` is the route behind it. It normalises what people actually type
  (lowercase, spaces, a missing hyphen) and validates the code's shape locally, so a typo is
  answered instantly instead of spending one of the API's five-per-minute enrolment attempts.
- **It only answers on loopback.** Anything else gets `403 not-loopback`. This matters: the
  Windows installer binds `0.0.0.0`, and `PRINT_BRIDGE_TOKEN` is empty by default, so without
  that gate a guest on the café wifi could pair the shop's bridge to their own organisation and
  receive every bill and kitchen ticket after it. Physical access to the till is the boundary —
  the same one `--enroll` has always used.
- A bridge that is **already paired** answers `409 already-enrolled`. Re-pairing to a different
  venue is possible with `{"code":…,"force":true}`, and reports `restart_required` because a
  running relay loop holds the previous token.

`--enroll` still works, unchanged, for scripted rollouts.

## Also

- `startRelay()` is now safe to call twice — it starts an unbounded work loop and a heartbeat
  interval, and a second concurrent loop would have two pollers claiming jobs in an order neither
  controls. This is what lets a freshly-paired bridge come online without a restart.
- The not-enrolled log line points at the local page instead of the command that could not be run.
