Local helper that prints POS receipts and labels on a venue's own hardware — over the network
(ESC/POS-over-TCP), a USB print queue, or a serial/Bluetooth port. It runs on a venue PC, not
inside the POS terminal's PWA, because a browser cannot open any of those. It also dials out to
the cloud API, so a phone or tablet can print through it without reaching the LAN. Install it on
**every till**, not on one shared PC.

**1.9.0 is a drop-in upgrade.** `relay.json` and `printers.json` are both kept as they are — an
upgraded bridge does not re-enroll, does not appear twice in the POS, and carries on printing
exactly as it did in 1.8.0. Everything below is about the one thing that was still hard: getting a
new computer connected to a shop in the first place, and getting a disconnected one back.

## Pairing now starts on this computer

**The code appears here, and the tablet scans it.** Until now a code was minted on a tablet and had
to be carried across the room to this machine, and the documented way to enter it — `--enroll` —
was never actually runnable: the binary is not on PATH under either installer, so following the
instructions produced `command not found`. Nobody types a URL, walks a code across a shop, or
retypes it any more.

When the bridge has nobody to print for, `http://localhost:9200` is a **QR code and an eight-character
pairing code**, filling the page. Open the Hankha app on a tablet or phone, go to
**Settings → Printing → Connect**, and point the camera at it. The seven diagnostic cards are still
there, behind **Details**.

- **Translated into English, Lao, Thai, Chinese and Vietnamese.** The rest of that page is a
  technician's screen and stays in English. This is the one screen a shop owner is ever sent to,
  and it was English-only.
- **The code renews itself when it expires**, so there is no expired screen and no button to press.
  Walking up to this machine ten minutes later still shows something you can scan.
- **The tablet never talks to the bridge** — both talk only to the cloud. That makes pairing behave
  identically on production and on localhost, and sidesteps the mixed-content and private-network
  rules that stop an HTTPS page from reaching `localhost:9200` at all.

## The installers open that screen for you

Nothing in either installer previously told an operator that a page existed: the address appeared
only in a log line, and the finish page sent them to the POS terminal instead.

- **Windows** — the finish page says a code is coming, and opens the pairing page by default
  ("Show the pairing code now" is ticked, so the common path is zero clicks). The Start Menu gains
  a **Print Bridge** shortcut, listed ahead of the status one. The old finish-page link pointed at
  `/health`, which shows raw JSON to someone whose question is whether the printer thing is working.
- **macOS** — the `.pkg` opens the pairing screen in the console user's session at the end of
  installation, and the `.dmg` app does the same when it starts the bridge. The final panel now
  says to scan the code on screen rather than to open Settings → Printing.

Opening a browser is best-effort everywhere: an unattended or SSH install has no console user, and
failing to open a window must never fail an otherwise good installation.

## A rejected bridge can be re-paired in place

If the server stopped accepting a bridge — it was removed from the shop, or its token was revoked —
the relay stopped and the logs pointed at that same unrunnable CLI. There was no way back except a
reinstall.

- **"Get a new code"** now appears on the pairing screen for exactly that state, and gets a fresh
  code without clearing the credential the bridge already holds.
- **Removed and merely offline are told apart properly**, from the pairing phase rather than by
  pattern-matching the last error string. A bridge that will never recover by waiting is offered
  the button; one that has simply lost the network is not, because it recovers on its own and must
  not be offered a control that throws a working station away.
- The **"not paired"** and **"token rejected"** log lines now name an address that exists.

## Under the hood

- **The QR encoder is vendored.** The bridge ships as a single compiled binary with no runtime
  dependencies, so there is no `qrcode` package to install. The SVG is built on the server: the
  page's content-security policy has no room for a bundled encoder, and a pairing code should never
  be reconstructed client-side from something weaker than the code itself.
- **`/pairing` and `/pairing/restart` are loopback-only**, gated exactly like `/enroll` and checked
  before anything else, so no later edit can widen them by accident. That page *displays a live
  pairing code* — anyone who can read it can claim this computer into their own organisation, so
  serving it to the venue's wifi would hand over the shop's printers to whoever asked first.

## The hosted bridge

Kubernetes deployment only (`k8s/prod`); no venue install is affected.

- **The relay identity now survives a restart.** `PRINT_BRIDGE_STATE_DIR` was empty, which fell
  through to a container-local path with no volume behind it, so `relay.json` — `install_id`,
  `bridge_id` and the relay token — died with the pod. Every restart came back unenrolled and
  needed a human, and because `install_id` was re-minted, re-enrolling created a *second* bridge
  row rather than reusing the original. It is now an explicit path onto a PersistentVolumeClaim.
- **The rollout strategy is `Recreate`.** `maxSurge: 25%` rounds up to 1 on a single replica, so
  the replacement pod started before the old one exited — which deadlocks on a ReadWriteOnce
  volume, and would otherwise leave two pods racing each other for the same claimed jobs.
- **Liveness is an HTTP probe on `/health`,** not a TCP one. The kernel completes a handshake from
  the accept backlog even when the event loop is wedged, so the old probe could never detect the
  one failure a restart would fix.
- **`PRINT_BRIDGE_TOKEN` moved out of the ConfigMap into a Secret**, and is now required rather
  than blank. An empty token makes every authorisation check pass, and that pod binds `0.0.0.0`
  behind a NodePort.
