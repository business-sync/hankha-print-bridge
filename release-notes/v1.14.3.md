# 1.14.3 — logs that can explain a disconnect

**Drop-in upgrade** (`relay.json` / `printers.json` untouched). No change to printing,
connection, retry or watchdog behaviour: this release is logging and diagnostics. Full guide:
`docs/print-bridge-debug-logging.md`.

## What was wrong

- The default log format (every installed bridge) printed only the sentence and dropped every
  structured field. A venue's `bridge.log`, usually the only evidence support gets, could not say
  which connection dropped, who closed it, with what error, or for how long.
- Several relay failures left no line at all:
  - heartbeat network errors;
  - websocket handshake failures;
  - frames that were not JSON;
  - message handlers that threw.
- A dropped socket always read `1006 connection lost`, whatever the real error was.
- A revoked token wrote the same `heartbeat rejected (HTTP 401)` line every 30 seconds for as long
  as it lasted.
- No uptime, memory, event-loop or timer-liveness information existed anywhere.

## What changed

- **Text log lines keep their sentence and add the fields** in `{event=… key=value}`. Warn,
  error and debug lines carry a level tag. Every record stays on one line.
- **JSON** keeps `ts`, `msg`, `level` and the snake_case fields, and adds `service`, `version`,
  `env` and `pid`.
- **Errors** carry `error_code` and the underlying cause (`cause_code`, which unwraps
  "fetch failed"). Unexpected errors also carry their stack.
- **Credentials are redacted** in every field: tokens, Authorization headers, URL userinfo and
  secret query values. Pairing codes are masked as `PSPN-****`.
- **Websocket sessions:**
  - a `connection_id` ties open and close together;
  - the close says `closed_by` (`local`, `remote` or `network`), the socket error, how long the
    session lasted, and when the last frame arrived.
- **Outages and recovery:**
  - New: `relay.recovered` with the down time, `relay.heartbeat.failed` and
    `relay.heartbeat.recovered`, `relay.transport`, `relay.reconnect_storm`.
  - `relay.stale` fires when the bridge is marked connected but nothing has arrived for three
    heartbeats.
  - Repeated failures are logged once and then every 10 minutes with a count.
  - `relay.retry` is now a warning, not an error.
- **Watchdog:** a line when its 15-minute restart clock starts and when it is cancelled, not only
  when it fires.
- **Process:**
  - `app.starting`, `app.config` (the effective settings), `app.ready`;
  - listen failures as structured errors;
  - drain time on shutdown, a shutdown-timeout line, and `process.exit` with the exit code.
- **Periodic `diag.snapshot`** every 15 minutes: memory, event-loop lag, relay timings, queue
  depth and stalled background timers. A stall over 1 s logs `diag.event_loop_lag`. The same
  numbers are on `GET /status` under `diagnostics`.
- **Printing:**
  - `print.sync.result` records what the POS was told for each `/print`, and `print.rejected` each
    request refused.
  - Queue lines gain `source`, `address`, `attempts` and `total_ms`.
  - At debug: every HTTP request and every send attempt.
- **Previously silent problems now logged:** torn spool files, an unreadable printers.json,
  settled-ring read failures, spooler and serial discovery errors, and log-clear failures.

## Notes for operators

- **New settings:**
  - `PRINT_BRIDGE_DIAG_INTERVAL_MIN` (default 15; 0 turns the periodic line off);
  - `PRINT_BRIDGE_DIAG_LAG_WARN_MS` (default 1000);
  - `PRINT_BRIDGE_ENV` (JSON `env` field).
- **To chase a problem:** set `PRINT_BRIDGE_LOG_LEVEL=debug` in `bridge.env` (Windows) or the
  launchd plist (macOS) and restart. Turn it off afterwards: the Windows log only rotates when the
  bridge starts.
- **Log parsers:**
  - Plain lines now end with a `{…}` field block, and non-info lines carry a level tag after the
    timestamp.
  - JSON keys are unchanged; new keys only.
  - A field that would collide with the envelope is renamed `field_<name>`.
