# 1.14.2 — a stuck printer no longer blocks its queue until a restart

**Drop-in upgrade** (`relay.json` / `printers.json` untouched). Mainly affects network (RAW/9100)
printers. The queue watchdog covers every driver.

## What was wrong

- **A printer queue could stop for good.** A network send only had an *idle* timeout, and any byte
  the printer sent back reset it. A printer that stops taking data (roll out, cover open, jam) but
  keeps answering with status bytes held the send open with no limit. Each printer's queue is
  sequential, so every later bill to it stayed `queued` and was never printed, failed or expired.
  Other printers kept working. Only restarting the service cleared it. Clear cache did not, because
  it leaves the job that is being sent alone.
- **A printer that was off was reported too late.** The connection attempt used the full 15 s
  send budget, but `POST /print` answers the POS after 8 s. So a ticket that provably never printed
  came back as `unknown`, and the POS did not offer a retry. This happened to online-order kitchen
  tickets (`accept-…`).
- **Kitchen tickets sent from the POS were lost when a printer missed the first connection.**
  After sitting idle, some printers ignore the first connection, including every retry on that
  same socket, but accept a new one a second later. Relay jobs retried and printed. Tickets the
  POS sends directly to the bridge (`accept-…` and order ids) got one attempt, so they failed
  with `connect-timeout` and only printed if someone pressed Retry on the POS.
- **The server's retries of a relay job did nothing.** When a job failed before connecting, the
  server queued it again under the same id. The bridge had remembered the failure, so it answered
  the redelivery from memory ("submitted twice … NOT reprinting") without trying the printer. All
  of the server's retries were used up in milliseconds.
- **Re-pairing from the QR code left the bridge offline for up to 5 minutes.** If the old token
  had been rejected, the relay kept sleeping with it after the new pairing, and the POS showed a
  freshly paired bridge as offline. Scanning a new code on a bridge that was still connected cost
  about a minute the same way: the old pairing was rejected a few seconds later, and the relay
  waited out a backoff before reading the new token.
- **Cancelled jobs left no trace** in the log, and plain log lines had **no timestamps**.

## What changed

- Network sends have two hard limits that printer traffic cannot extend:
  - Connecting: `PRINT_BRIDGE_CONNECT_TIMEOUT_MS`, default 5 s. A failure here is
    `connect-timeout` / `none`, so it can be retried.
  - Sending: `PRINT_BRIDGE_SEND_TIMEOUT_MS`, still 15 s, counted from connect. A failure here is
    `write-timeout` / `unknown`, and it is never reprinted.
- `POST /print` now retries a ticket that provably never reached the printer, within the POS's
  8 s wait. Each attempt gets at most 2 s to connect, and no attempt starts unless it can finish
  before the POS stops waiting. In the worst case that is two attempts, with more when the printer
  refuses at once. A ticket that might have printed is still never retried. The log shows
  `failed (connect-timeout) but nothing printed — retrying in 1s`, as for relay jobs.
- Queue watchdog: if any driver is still sending 10 s past the send timeout, the job is settled as
  `write-timeout` / `unknown`, the next job runs, and `queue.stalled` is logged.
- A relay job that failed before reaching the printer (`printed_certainty: none`) is no longer
  remembered. The server's retry now really tries again. Cancelled and expired jobs, and anything
  that might have printed, are still answered from memory and never reprinted.
- Pairing by QR wakes the relay at once, as pairing from the local page already did. When the
  relay's token is rejected, it first checks for a newer saved pairing and switches to it at once.
  New log line: `relay: switched to the new pairing (bridge N)`.
- New log line `queue: job … cancelled before printing` (`queue.cancelled`). Plain-format log lines
  now start with the computer's local time (`2026-10-22 13:46:57 …`).

## Notes for operators

- **After upgrading, do not scan a new code** unless the bridge page says it is not connected.
  The installer's finish page opens the pairing screen, but scanning there replaces the pairing
  that was already working.
- **A kitchen printer that often fails on the first try** is worth checking. Wi-Fi power saving is
  a common cause. The bridge now covers it, but a wired connection, or turning power saving off on
  the printer, fixes it at the source.
- **Long jobs:** a single send must now finish within `PRINT_BRIDGE_SEND_TIMEOUT_MS` of
  connecting, even while the printer is still taking data. Normal bills and logo receipts take well
  under a second. Raise the value (up to 120000) only for very large label or raster jobs on a slow
  printer.
- **A stalled bill** now shows as a `write-timeout` failure about 15 s after it started. Check the
  printer's paper and cover. The bridge does not reprint it automatically, because part of it may
  already have printed.
- **Log parsers:** plain lines now have a timestamp prefix. JSON format
  (`PRINT_BRIDGE_LOG_FORMAT=json`) is unchanged.
